## 1. How APEX calls the package

Every public member is called with **named binds**, one line per page component:

```sql
-- Validation "BUS_ID VALIDATION" (PL/SQL Function Body returning error text)
RETURN IMPR1110.BUS_ID_VALIDATION(P_BUS_ID => :P1110_BUS_ID, ... );

-- DA "BUS_ID WHEN-VALIDATE-ITEM" (FOS Execute PL/SQL Code; Items to Submit = IN and IN OUT items,
-- Items to Return = IN OUT items)
IMPR1110.BUS_ID_WHEN_VALIDATE_ITEM(P_ARBC_IMPR_NAME => :P1110_ARBC_IMPR_NAME, ... );

-- Item P1110_BUS_ID, Read Only: PL/SQL Expression
IMPR1110.BUS_ID_IS_READ_ONLY(P_IMPR_NBR => :P1110_IMPR_NBR, P_CODE => :P1110_P_CODE,
                             P_IMPR_TYPE_CD => :P1110_IMPR_TYPE_CD,
                             P_BUS_ID_TYPE_CD => :P1110_BUS_ID_TYPE_CD)
```

Parameter names (package 008, `scripts/parameter_names.py`): no `I_` / `IO_` / `O_` prefix; a page item `P<page>_X` is passed as `P_X` and a Forms-parameter item `P<page>_P_X` as `P_X` too (no doubled `P_P_`), application items keep their name, except in `PARAMETERS_ENTRY`, which receives both: there the application items are `APP_P_PRSNL_IMPR` / `APP_P_LETTER_NBR`; inside SQL a parameter is qualified with its member name. Inside each entry point the parameters are copied into
the private record `r` (block IMPORTERS) and context `c` (`:PARAMETER.*`), the converted Forms logic runs,
and the changed fields are copied back to the IN OUT parameters. The lists are **computed**, not written by
hand: the generator follows the call graph of the private logic and collects every `p_rec.<field>` /
`p_ctx.<field>` that is read, assigned, or filled by `SELECT / FETCH / RETURNING … INTO`.

| Forms | Record field | APEX item | Parameter |
|---|---|---|---|
| `:PARAMETER.P_CURR_PORT_CD` | `c.curr_port_cd` | application item `P_CURR_PORT_CD` (f345) | `P_CURR_PORT_CD` |
| `:PARAMETER.P_USER_ID` | `c.user_id` | `SSO_APP_USER` (f345) | `SSO_APP_USER` |
| `:PARAMETER.P_WS_ID` | `c.ws_id` | `P_GLOBAL_V_WS_ID` (f345) | `P_GLOBAL_V_WS_ID` |
| `:PARAMETER.P_CLASS_CD` | `c.class_cd` | `P_CLASS_CD` (f345) | `P_CLASS_CD` |
| `:PARAMETER.P_USER_TYPE` | `c.user_type` | `V_USR_TYPE` (f345) | `V_USR_TYPE` |

Control fields of the record are derived, never passed by APEX:

| Field | Derived from |
|---|---|
| `rec_status` | the entry point (`'INSERT'` in PRE/POST_INSERT, `'CHANGED'` in PRE/POST_UPDATE, `'QUERY'` in POST_QUERY, `'NEW'` in WHEN_CREATE_RECORD), otherwise `NEW` when `P_ROW_ID` is null, else `QUERY` |
| `row_id` | `P_ROW_ID` (the ROWID primary key of the Form region) |
| `activity_entr` | `NOT ACTIVITY_IS_READ_ONLY(bus_id, activity)` (Forms `GET_ITEM_PROPERTY(ACTIVITY, ENABLED)`) |
| `bus_id_brnch_entr` | `NOT BUS_ID_BRNCH_IS_READ_ONLY(...)` |

Confirm answers (Forms `SHOW_ALERT` = `ALERT_BUTTON1`) come in as `P_ANSWER` / `P_SUSPEND_ANSWER`
(`DEFAULT NULL` = yes). The page asks the question with a native **Confirm** action whose text comes from a
`*_CONFIRM_TEXT` function.

`READ_ONLY_FLAGS` returns the same rules as Y/N values (`O_<ITEM>_LOCKED`) for the hidden items
`P1110_<ITEM>_LOCKED`. The page needs them because a Read Only condition is evaluated only when the page is
rendered: after a change of IMPR_TYPE_CD, BUS_ID_TYPE_CD, COMM_RGSTRTN_TYPE, BUS_ID or BUS_ID_BRNCH, the DA
calls `READ_ONLY_FLAGS` and native Enable / Disable actions apply the flags (f345 §9, no JavaScript).

The private helpers `PRIVATE_SAVED_RECORD_LOCKED`, `PRIVATE_IMPORTER_TYPE_LOCKED` and
`PRIVATE_REGISTER_MATCHES` hold the three shared rule groups, so each item function is 3–10 lines.
